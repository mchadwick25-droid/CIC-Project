# One-document-at-a-time build protocol

This governs how a world is built. It replaces batch construction with a single, repeatable cycle applied to each document in turn.

## Setup, once at the start of the thread

1. Confirm branch (`git branch --show-current` must read `main`) and clean state before reading anything.
2. Read the filed Step 0 conclusion **in full — all nine confirmed worlds, not only the one you may end up building.** This branch was deliberately built to include the complete nine-world context so that the eventual build has real contrast and boundaries to reason against from the start.
3. **Produce and present a nine-world boundary and contrast review before any world is selected.** For each of the nine worlds: its core distinguishing gravity in one or two sentences, its nearest neighbor(s) among the other eight and exactly what keeps them separate (not just geography or period — formation-logic, authority structure, relationship to power), any residual overlap risk worth naming, and the specific open issues already on record in the Step 0 conclusion for that world (scope questions, floor-proximity concerns, recentering obligations, provisional status). This is shown in full to the project lead, who picks which world to build from it — the thread may note which world looks like the clearest or most instructive starting point, but does not pick for the project lead.
4. Once a world is selected, read the Construction Framework in full (now the only version of it on this branch) and produce an explicit, numbered list of the actual current document sequence (Doc_01 through Doc_10, or whatever the current framework actually specifies) with a one-line description of what each document must contain. **Present this list before doing any construction work.** Do not assume any document list from memory or from a prior version — derive it fresh from what's actually in this branch's copy of the Framework, and flag plainly if the sequence or numbering has changed from what any prior world build used.
5. Wait for confirmation of the document sequence before starting Doc_01.

## The per-document cycle — repeats for every document in the sequence

1. **Draft.** Produce exactly one document — the next one in the confirmed sequence, nothing further ahead. Do not draft, outline, or pre-write any later document while a current one is open.
2. **Independent review.** An adversarial review prompt specific to this document is prepared and run in an isolated review. The review result is saved as its own file, next to the document it reviews — `Doc_0N_Review_RoundM.md`, not a paragraph in a revision log or a sentence in the document's own status line. A review that exists only as a claim inside the document being reviewed did not happen, regardless of how specific or convincing that claim reads. The review should check: factual/historical accuracy of any claims, internal consistency with the Step 0 conclusion's scope and known issues for this world, Author Gravity discipline (source attribution, confidence calibration), and whether the document does the job this stage of construction requires — not just whether it reads well.
3. **Revision decision.** If the review calls for **substantial** revision — a change to a claim's substance, a confidence rating, a sourcing conclusion, a scope boundary, or anything a reader of the document would notice as different — the document is revised and sent back through step 2. This repeats until a review no longer calls for substantial revision. Minor, cosmetic, or wording-only suggestions do not require a fresh review cycle; they're applied and noted, but the review that found them still gets saved as its own file, even when its own verdict is "cosmetic only."
4. **Escalation check.** Before disposing of the document, check it against the four standing escalation categories below. If any apply, stop here and escalate directly to the project lead — do not self-dispose.
5. **Disposition.** If no escalation trigger applies and the review cleared with nothing substantial outstanding, the build thread applies **Approved to proceed** itself — a lightweight go-ahead, unblocking the next document, claiming nothing about completeness. This does not require a per-document reply from the project lead. **Frozen** is different in kind: it requires the project lead having actually seen the complete document and the complete review artifact(s) and made a deliberate, considered closure decision — a build thread never assigns Frozen itself, on any reading of any reply, ambiguous or not.
6. **Log it.** Every document that reaches Approved to proceed is logged as a dated Decision Log entry: document name, review outcome, revision count, the filename of each review artifact, and which disposition it received. This log is what a coach thread's periodic verification pass checks against. Only once a document reaches at least Approved to proceed does work begin on the next document in the sequence — reaching Frozen is not required to move forward.

## Escalation to the project lead

Four categories always go to the project lead directly, in full, regardless of how the rest of the cycle runs:

- **Representative identity, name, or title decisions** — every one, including a later change to an already-decided identity, not only the first decision made for a given world. These must use the grounded-options format: named alternatives, an explicit trade-off for each, a recommendation, and a dedicated decision artifact (its own file, cross-referenceable from anywhere the decision is used) — discussed directly with the project lead before the decision is used anywhere else in the build.
- **Portfolio-level or cross-world strategic decisions** — anything decided for a reason external to this specific world's own ecology (for instance, choosing an anchor or emphasis to diversify against other CiC worlds). Any document recording such a decision must label it explicitly as portfolio-level, distinct from an ecology-grounded finding.
- **Governance or methodology decisions** — anything that changes how the build process itself works, including changes to this protocol.
- **Unresolved tensions the pipeline can't close on its own** — two reviews disagreeing with each other, a contradiction discovered between two already-cleared master documents, or a finding that cuts against a decision made earlier in the build.

## Naming and term propagation

Whenever a name or term changes — a Representative's name or title, a lexicon term's preferred form, anything that appears in more than one place — check every file it appears in before treating the change as complete: the narrative document, any companion index spreadsheet, and any deployment lexicon chunk. A fix that lands in the narrative document without the index being updated to match is not a complete fix.

## Cross-document fact consistency

When two documents in the same world's build state the same specific claim — a fact, a number, a quoted phrase, a piece of terminology — drawn from the same underlying source material, check that they actually match, or that any difference is deliberate and disclosed. This has caused two real defects in this project's history: World #7's Doc_02 and Doc_03 independently asserted contradictory claims about the same vocabulary term (one treating it as attested, the other excluding it as unattested) without either document cross-checking the other; and World #1's Permanent Prompt and World Capsule Core independently restated the same underlying fact using different wording ("kept" versus "survives"), caught only when a later review misattributed a quote from one document to the other. Where the same claim needs to appear in more than one document — which it often should, since the Permanent Prompt and Capsule Core are both always-present together and cover genuinely overlapping ground by design — carry the exact wording across, or state plainly why the wording differs. This applies most directly to Permanent Prompt/Capsule Core pairs, but the same check applies to any two documents in a world's build that draw on the same source material to state the same thing.

## Coach verification

A coach thread performs periodic independent verification across a batch of work a build thread has already disposed of — checking review artifacts actually exist and actually support what they're cited for, checking escalation triggers weren't missed, checking the Decision Log matches what's actually on disk, and checking that the builder's actual decisions match the build's own governing designs (the Framework, prior identity decisions, prior ecological findings), not only that a file exists and was reviewed. This replaces per-document gating, not the underlying discipline. The coach thread reports findings to the project lead directly; it does not draft or revise world-build documents itself. Editing authority over this protocol and the other non-world-build governing files (the Construction Framework, the Representative Construction Framework, the Change Orders Register, the L3B/L4 templates, and — added 2026-07-28, see the Fifth revision note above — `Build/reference/L0-Reference/L0_Doc_00_Boundaries_and_Standards.md`) belongs to a coach thread — a build thread's write access is scoped to its own world's build folder. **Exception:** a coach thread may also make small, purely technical corrections directly inside a world-build file — a citation misattribution, a broken cross-reference, a propagation fix, a formatting error — provided the correction changes no substantive claim, finding, or decision, and is disclosed inline with a dated correction note rather than silently rewritten. Anything that touches substance — a conclusion, a verdict, a scope boundary, a piece of content a participant might eventually see — stays with the build thread, or goes through the escalation categories above if it's genuinely unresolved.

## Rules that hold across every cycle

- No document is worked on out of sequence, and no later document is drafted while an earlier one is still open.
- Nothing is shown in summary form at any review or sign-off point — full documents, full review outputs, every time.
- A document is never advanced to any disposition on the strength of the coaching thread's own judgment alone; it requires an independent review that did not call for substantial revision, saved as a file.
- **A document's own status line — "Cleared review," "Approved to proceed," or "Frozen" — is not evidence and settles nothing on its own.** Each is a label a document carries after the real thing happened elsewhere (a review that exists as a file, a disposition the project lead actually made) — never the mechanism by which it happens.
- **No document reaches Frozen on a build thread's own interpretation of an ambiguous reply.** This is a standing rule. Any reply that isn't unambiguously a deliberate act of closing the document out defaults to Approved to proceed — never resolved upward in the direction of the stronger-sounding status.
- Before drafting or revising anything, check whether a version of this exact document already exists in the canonical project folder marked Approved to proceed or Frozen. If it does, and there is no project-lead-visible record — the review artifact files plus an actual disposition — that it was genuinely reached, **stop** and flag the conflict explicitly. Do not proceed as though starting fresh, and do not treat the existing file as settled ground truth either. An existing file's presence is not proof of anything on its own.
- If a review disagrees with an earlier review on the same document (for instance, a second-pass review reopening something a first pass cleared), that disagreement is logged explicitly rather than silently resolved in favor of whichever review came last.
- **A review finding is never dismissed as a tooling or environment artifact (a stale cache, a mount discrepancy, and so on) without independent re-verification confirming the dismissal itself.** The finding stands until that re-verification actually happens and actually confirms the dismissal — not on the strength of the dismissal being asserted, however confidently.
- **Nothing is attributed to "the project lead" in any document — a quote, a decision, an instruction — without a verifiable record that the project lead actually said or wrote it.** This is held to the same evidentiary standard as a Frozen disposition: a real, checkable record, not a claim.
- **Content described as having been "shown" or "posted" to a coach thread must actually be included, verbatim, in what the coach thread receives.** A claim that content was already shown is not a substitute for including it.
- **All build output is written to the canonical shared worlds folder for that world — never to a thread-local or session-scratch path.** If a path outside that folder is in use, it is corrected before continuing, not worked around.
