## 2026-07-20 — Pilot 1 gating removed: no sign-in, no pre/post-survey, informal access control instead

**Decided (Mark's direction):** the pilot plan's gated process — sign-in screen, pre-survey, scripted-question-only threads, post-survey, invite-code/forward-credit tracking, the self-serve Google Docs package (all of `CiC_Prototype_Testing_Pilot_Plan_DRAFT_V0_1.md` Section 8, and the sign-in/survey framing in Sections 1/3/4/5) — is dropped. Mark's own words: *"it is still very small audience, so lets remove the whole process and we will put the system up on the website like it will be when we go public, let them experience everything as it will be. i will ask them not to forward the link of the website to anyone unless we talk. it makes everything easier and i will be careful to watch if it gets more users."*

**What replaces it:** the real app, deployed close to how it will look at public launch, reachable by anyone with the link. No app-level identity, no gate screen. Access is controlled entirely outside the app — a personal request to each tester not to forward the link without checking with Mark first, plus Mark watching traffic for signs of unexpected spread. This is a deliberate trade: it gives up the structured pre/post-survey data and the forced two-scripted-thread design, in exchange for testers experiencing the actual product rather than a scaffolded testing harness around it — which is itself closer to Article 6's real question (does the encounter hold up on its own) than a heavily-instrumented version of it would be.

**What stays, unchanged:**
- **Server-side transcript logging** — stays on unconditionally. This was already justified independently of the survey apparatus (Section 4's own reasoning: Article 6 violations usually can't be diagnosed from a tester's memory after the fact, only from the transcript) and nothing about today's decision touches that reasoning.
- **The in-app sign-in/survey code** — `SignInScreen.tsx`, `cic-poc/backend/app/auth.py`, `session_cap.py`'s Supabase-backed per-identity capping — is left in place, unused, not deleted. Both the frontend gate (`TheTable.tsx`'s `isSignedIn` state) and the backend gate (`auth.py`'s `get_current_user`) already default to fully bypassed/no-op behavior whenever Supabase isn't configured (no `SUPABASE_URL`/`SUPABASE_SERVICE_KEY` set) — confirmed by reading both files directly. **Removing the in-app gate for this pilot required zero code changes**; it only requires never configuring Supabase for this deployment. Kept rather than deleted in case a later, larger-audience phase wants identity back.

**Correction to my own initial framing — `pilot.html` is not actually dormant.** When Mark answered "leave it in place, unused" to my clarifying question, the shared assumption was that `cic-website/pilot.html`/`pilot-thank-you.html` were leftover scaffolding from the old gated-pilot design. Checked directly and that's wrong: `pilot.html` is the live "request access" landing page, and it's linked from the site nav and from `index.html`, `about.html`, `atlas.html`, `tour.html`, `support.html`, and `refer-a-friend.html` — it's the site's only current path to the app, not an unused artifact. It's a mailto "express interest" form ("Mark will personally follow up before anything is set up"), not a sign-in/survey gate, and its `PILOT_REQUEST_API` hook is empty/inert (no backend wired), so nothing here contradicts the message-cap or transcript-logging decisions above. But it is still a manual-approval step between a visitor and the live app, which is arguably still part of "the whole process" Mark asked to remove, or may be exactly the informal control he described ("I will ask them not to forward the link... I will be careful to watch") implemented slightly differently than assumed. **Not resolved — flagged back to Mark rather than guessed at; no website file touched.**

**New engineering, the one real gap this decision opens:** `session_cap.py`'s per-identity session cap becomes a permanent no-op with no signed-in identity to key off — every visitor is functionally anonymous. Since Mark is deliberately trading structural gating for informal watching, a lightweight technical backstop still made sense as a second layer under the Anthropic Console spending cap and Mark's own traffic-watching, for the case of a genuinely runaway session (the link spreading further than intended, a stray script, a tab left open in a loop) rather than the case of a normal engaged conversation. Built `cic-poc/backend/app/message_cap.py`: a soft, identity-free ceiling checked against `state.turn_count` (one Representative turn = one increment, so it's a direct proxy for API spend on that session), defaulting to 60 turns, deliberately generous rather than tight. Wired into both `main.py` endpoints (`send_message`, `send_message_stream`) at the earliest safe point in each — checked immediately after loading `state`, before any classify-then-route intercept runs, so a capped session never reaches representative-generation at all. When the cap fires, the round ends with a single graceful facilitator message instead of an error. Committed `6ee48fc`.

**A note on how this was committed:** at the time this was built, another concurrent session had active, uncommitted changes to the same file (`main.py`, plus `facilitator_prompts.py` and a new `epistemology_bridge.py` — an unrelated fourth classify-then-route intercept). Rather than a normal `git add`, the two cap-check hunks were isolated into their own patch and applied to the index with `git apply --cached`, verified via `git diff --cached`/`git diff` that only the cap-check hunks were staged and the other session's hunks remained untouched in the working tree, then committed alone. Confirmed post-commit that the other session's uncommitted diff was still intact and `main.py` still compiled with both sets of changes coexisting.

**Checked directly, confirmed still accurate:** `OnboardingScreen.tsx`'s in-app disclosure ("This is a prototype, not a finished product" / "We're cataloging this conversation... reviewed by the project team only") is self-contained and shown once per visitor before they pick a world (a `localStorage` flag, not a Supabase gate) — it doesn't reference or depend on a separate pre-survey/Orientation Doc existing elsewhere, so it needs no change now that it's the only pre-conversation framing a visitor sees. No edit made.

**Still open, not resolved here:**
- `Ministry/Features/Prototype-Testing/CiC_Prototype_Testing_Pilot_Plan_DRAFT_V0_1.md` carries a V0.4 note at the top marking Sections 1/3/4/5/8's gating framing as superseded, keeping the content itself (onboarding text, question sets) as reasoning trail — Section 5's pre-scripted threads are still useful as suggested starting questions, just no longer a mandatory gate.
- Actually standing the simplified deployment up (hosting, `#101/401` on the System Hub Task Board) is unchanged by this decision and remains open work in its own right.

## 2026-07-20 (later) — `pilot.html`'s access-request question resolved: link straight to the app

**Decided (Mark's direction, in answer to the open question above):** *"link to the app and let them experince everything as it will be."* `cic-website/pilot.html` no longer treats the mailto "express interest" form as the way in. Confirmed first that neither the app nor the marketing site has a real hosted URL yet (`Ministry/Operations/Standing/CiC_Task_Board_2026.md` #101/401 is still open — no Render/Fly.io/Vercel/Cloudflare Pages config anywhere in the repo, `cors_origins` still only lists localhost), so this is a structural change made ahead of hosting, not something live-tested against a real deployment yet.

**What changed on the page:** a prominent primary CTA ("Come and join us at the Table," the Kit's own verbatim phrase) now sits right after the hero, wired to a `LIVE_APP_URL` constant left empty until #101/401 lands — shows an honest "hosting is still being finished, check back soon" message rather than a broken or fake link in the meantime, same discipline as the page's existing `PILOT_REQUEST_API` placeholder. The mailto form stays on the page but demoted from the primary action to an explicitly optional "let Mark know you stopped by" — button downgraded from `btn primary` to `btn secondary`, copy rewritten so it no longer implies visitors need to wait to hear back before using the link above. Verified visually in the browser preview in both the pending state (current, real) and the live state (simulated by setting `LIVE_APP_URL` via the console, not by deploying anything). Committed `9efe0c2`.

**A real conflict surfaced while doing this — Mark's call: hold.** Another concurrent session (the UX design thread) has active, uncommitted work in `cic-poc/backend/app/main.py` building `/api/pilot/request`, `/api/referral/generate`, and `/api/referral/redeem` — a Supabase-Auth-gated flow where Mark reviews each `pilot_requests` row and invites people individually, plus a one-hop referral-code system for invited testers to bring a friend. It isn't live today — every one of those endpoints is a documented no-op while Supabase stays unconfigured, same discipline as everything else Supabase-dependent — so nothing is broken by either piece of work coexisting in the tree right now. Flagged to Mark; his direction was to hold and let the UX design thread finish its own updates rather than interrupt it mid-work. **Reconciling the two directions is deferred, not resolved** — revisit once that thread is done, not before.

**Not touched, deliberately:** `cic-website/pilot-thank-you.html` (the post-conversation "thank you" / refer-a-friend page) — it isn't part of the entry gate this decision concerns, nothing currently links to it, and Mark's instruction was specifically about linking in, not about the post-conversation page.
