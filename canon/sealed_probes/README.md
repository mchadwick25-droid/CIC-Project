# Sealed held-out admission paraphrases

Stage 3 deliverable (Build-Blueprint.md §5): "every cell has sealed probes
before any world answers it." One probe per canon cell (28/28), a genuine
paraphrase of a real Appendix A question — never the exact canon string
(canon maintenance rule 3, `CiC-Program-Spec.md` Appendix A).

## Access rule — read this before touching anything under `plaintext/`

**No world-build code path may read `plaintext/`.** Not `engine/m1` (gates),
not `engine/m2` (the compiler), not any future world-build tooling, not an
AI thread building a world's records. Only the M3 admission harness (stage
4, not yet built) may read a probe's plaintext, and only at grading time.

Why this matters: if a world's records were shaped — even innocently — to
match a probe's exact wording, admission would stop testing what it's for
(whether the world can answer questions it was never shown). `seals.yaml`
exists so that wording is provably fixed *before* any world touches the
canon, and `engine/canon/check_seal_isolation.py` (wired into CI) is the
automated backstop for the access rule stated here — a rule nobody reads is
a rule nobody follows.

## What "sealed" means here — and what it doesn't

This is a **commit-reveal scheme, not real secrecy infrastructure**. No
secrets manager or access-controlled store exists yet — the whole record
store is one shared git repository (Artifact-1 §1), so anyone who can read
this repo can read `plaintext/` directly. What sealing *does* provide:
`seals.yaml` commits a sha256 of each probe's exact plaintext bytes now,
before any world exists to answer it — so a later edit to a probe's wording
is detectable (the hash changes), and the access-discipline guard makes
"a world-build path read the sealed wording" a CI failure, not a silent
possibility. That is real, useful protection against the two likeliest
accidents (silent post-seal rewording; a builder script or agent
accidentally reading probe text while building a world) — it is not
protection against a determined reader of this repository. Real
access-controlled sealing (a genuinely separate, permissioned store) is an
infra decision for whenever secrets/permissions infrastructure exists,
plausibly alongside stage 6's AWS setup — `DECIDABLE`, recorded here rather
than silently presented as more secure than it is.

## Layout

- `seals.yaml` — the committed seal: per cell, `probe_id`, `sha256` of the
  plaintext file, `sealed_at`, `status`.
- `plaintext/<probe_id>.md` — the probe text itself, plus `paraphrase_of`
  (which canon_question id it paraphrases — for stage-4 provenance/audit
  only; graders never see that id).
- Generated by `engine/canon/seed_admission_paraphrases.py` — see that file
  for the full table and the reasoning behind each choice.
