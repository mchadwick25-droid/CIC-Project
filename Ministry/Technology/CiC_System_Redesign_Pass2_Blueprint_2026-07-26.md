## 0. How to use this blueprint — the session contract

This blueprint is executed by **Sonnet sessions, one step at a time** (per the standing model-tier allocation: Sonnet builds and compiles; Opus runs review passes; Fable is not in the execution loop). Every build session follows the same contract, and the contract is the first defense against the failure this whole redesign exists to fix — because incremental session-by-session building is exactly the process shape that produced the fan-out/drift record (a fix landing where the reviewer looked while the same fact stayed stale elsewhere; a claimed fix that was never delivered; a companion artifact never regenerated).

**The session contract — every build session, no exceptions:**

1. **Read the build-state ledger first** (`Ministry/Technology/Pass2/BUILD_STATE.md`, created in step S1.0). It names the current step, the last completed checkpoint, and any parked items. A session never relies on memory of a previous session — all state lives in committed files.
2. **Re-run the previous step's checkpoint before starting your own work — what "re-run" means depends on the checkpoint kind, stated here so no session has to guess.** For G/B checkpoints (deterministic scripts): literally re-execute the script; it must reproduce the same result. For content-coverage parity: literally re-diff. **For R, P (probe-parity), and L checkpoints, which depend on a specific sample, a specific set of held-out probes, or blind grading — "re-run" means re-checking the artifact's own committed sample IDs, probe list, or battery transcript against the underlying records/code, not drawing a fresh sample or re-blind-grading with different material.** The committed artifact must include those IDs/lists for exactly this reason — an artifact that only states a verdict, with no way to re-derive it against the same rows, does not satisfy this rule. If the previous checkpoint no longer passes under this check, stop: the step is not "do my step anyway," it is "file the regression and halt." This is how a claimed-but-not-delivered fix gets caught at the next session instead of three worlds later.
3. **Do one step. Only that step.** The step spec names every file it is allowed to touch (`Touches:`). Changing a file outside that list is not forbidden by the tooling — it is caught by the checkpoint reviewer, whose first structural check is the diff against the declared file set. The fan-out list is precomputed *here*, not left to session judgment.
4. **Never edit a gate or checkpoint script in the same session that must pass it.** Gate changes are their own steps with their own review. A session that needs a gate changed to pass files a flag and stops.
5. **A step is done when its checkpoint artifact exists, is committed, and re-runs green — not when the session says so.** The checkpoint definition lives in this blueprint, written before any session ran; the executing session cannot move its own goalposts.
6. **If you find a defect in the Pass 1 design, in this blueprint, or in a previous step's output: stop and file it** (append to `Ministry/Technology/Pass2/FLAGS.md`, with the evidence). Never silently patch around it, never silently fix it in passing. Whether to change course is Mark's call or a review-round call, not a mid-session judgment.
7. **End every session deployable.** No step leaves the running system half-migrated. The compatibility rule (§3.2) exists so this is always possible. If a session runs out of room mid-step, it commits what is consistent, marks the step `in-progress` in the ledger with a note on exactly where it stopped, and the next session restarts the step *from the last green checkpoint* — not from a description of partial work.
8. **Every step's outputs are committed with the step ID in the commit message.** The ledger, the commits, and the checkpoint artifacts are the same story told three ways; a mismatch between them is itself a filed flag.

**Why this contract is shaped this way:** the six-world defect record shows written rules alone failing repeatedly (a standing rule against self-certification was adopted at the second world built and the identical pattern recurred in the third, fourth, and sixth). So this contract leans on the same conversion Pass 1 §4.2 makes for build gates: **everything that can be a program is a program** (re-runnable checkpoints, declared file sets, committed artifacts), and what can't be a program is an *independent* review with a saved artifact — never the builder grading their own work.

## 1. The checkpoint problem, answered

The brief names the hard problem directly: a verification checkpoint at each step, "not a self-report." Six mechanisms, used throughout:

| # | Defense | What it prevents |
|---|---|---|
| 1 | **Prospective definition.** Every checkpoint below is defined now, in this document, before any executing session exists | The executing session defining its own success criteria |
| 2 | **Committed, re-runnable artifacts.** Every checkpoint emits a file (gate report, diff, review, baseline) that is committed and can be re-executed by anyone | "Fixed/confirmed/complete" claims with nothing behind them — the single largest defect category in the six-world record |
| 3 | **Entry re-verification.** Each session re-runs the prior checkpoint before its own work | A broken or faked prior step propagating silently |
| 4 | **Machine wherever possible; independent review where not.** Gates, parity diffs, and harness runs are deterministic programs. Content judgment goes to a fresh-context Opus review with no access to the builder session's reasoning, saved as an artifact, no self-certified dismissals (CO-020/CO-022, carried forward). Voice grading is blind and two-trial per the V7.4 Validation Protocol Rigor discipline | Plausible self-assessment standing in for verification |
| 5 | **Seeded-defect testing of the gates themselves** (S1.3). Every gate ships with fixtures it must *fail*. A gate that never fails checks nothing — Pass 1 §10's own health rule, applied to the checkpoint layer before anything depends on it | Checkpoints that are green because they're vacuous |
| 6 | **Baseline-before-change** (Pass 1's own sequencing rule, §5.4 R0 and §10). Every behavior-changing step compares against a baseline committed *before* the change. A baseline measured after the fix is not a baseline | Unfalsifiable improvement claims |

**Checkpoint taxonomy used in every step spec below:**

- **G — gate:** deterministic machine check; committed report; re-runnable. (Validator runs, referential integrity, reciprocity, field completion, readability, harness regression.)
- **P — parity:** regenerate or replay, then diff against a committed reference. Four kinds: *render-parity* (a generated view against the deployed artifact it replaces), *replay-parity* (recorded request suites through old and new code paths — driven from recorded real classifier responses where the classifiers' own behavior is what's being verified, `mock_llm` only for the streaming/plumbing half where LLM variance would drown the diff and no classifier firing needs to be observed — see S4.1), *probe-parity* (the same validation probes against old and new voice, diffed, blind-graded — Pass 1 §5.2's continuity regression), *content-coverage parity* (S2.2: every sentence of a source document lands in exactly one migrated field or an explicit, logged `dropped:` entry — nothing silently lost, nothing silently duplicated).
- **R-lite:** a lighter-weight review than a full batch R — used where the review standard practice's discipline still applies (an independent check, no self-certification) but the artifact is small enough that a single-pass check suffices rather than the two-round minimum full content review uses. Where used below (S1.1, S3.1, S6.3), the specific check performed is stated in that step's own checkpoint line.
- **L-lite:** a single scripted live conversation (not a full multi-case battery) confirming one specific end-to-end behavior, with its expected-behavior column filled and the transcript committed — smaller than an L battery, but still a real live run against the deployed system, never a description of expected behavior standing in for one. Where used below (S3.4, S5.3), the specific behavior confirmed is stated in that step's own checkpoint line.
- **R — review:** independent fresh-context Opus review against the step spec and Pass 1's cited sections, per `CiC_Adversarial_Review_Standard_Practice.md`. Saved artifact. Counted structural checks, not impressions.
- **B — baseline:** a measurement committed before its change ships; named as the comparison object by later steps.
- **L — live battery:** a scripted live-model test with expected behavior per turn and a filled scorecard, modeled on `CiC_Live_Safety_Testing_Script_2026-07-21.docx` — the project's own proven instrument for this.
- **M — Mark:** an explicit decision, presented singly (one decision at a time), recorded in the Decision Log before dependent steps proceed. Non-dependent work continues while an M is pending — nothing idles waiting on a decision it doesn't need.

**Two standing rules that apply across all phases:**

- **Safety regression rule:** any step that touches the intercept chain, `main.py`'s endpoint bodies, conversation state, or the public transcript ends with a rerun of the live safety script (all batteries, filled scorecard, committed). The 19/20 record is the floor; any new failure is a halt-and-flag. A.4 (de-escalation timing) remains the known borderline until S4.2's event log makes it diagnosable; it is re-diagnosed then, not tinkered with before.
- **Retrieval regression rule:** any step that touches indexing, retrieval, ranking, or query construction ends with a harness run diffed against the committed baseline; `do_not_retrieve_when` violations must be 0 and no tracked metric may regress without a filed flag. **The committed baseline is B-RETR (S1.2's current-system measurement) through the end of Phase 3.** Phase 3 exists to improve retrieval, so its own final step (S3.5) commits a new post-Phase-3 baseline; every retrieval-touching step from Phase 5 onward (S5.3's R7) diffs against that one instead. If Phases 2 and 3 interleave (§2 permits this), the comparison object for any Phase-3 step must be stated explicitly in that step's checkpoint report — never left implicit.

## 2. What Pass 2 is building, in dependency order

The design decomposes into five workstreams with real dependencies:

```
Phase 1  MEASURE & PIN         baselines, harness, gates, schema, parameters
            │                   (nothing about the product changes)
            ▼
Phase 2  FIRST MIGRATION       one world's records + views, render-parity,
            │                   runtime untouched (compatibility rule)
            ├──────────────► Phase 3  RETRIEVAL REBUILD (R1–R6, R8, R9)
            │                   harness-gated, world-format-agnostic
            ▼
Phase 4  GOVERNANCE ENGINE     one layer, event log, turn selection,
            │                   bridge, repair, grounding — battery-gated
            ▼
Phase 5  VOICE & ACCESS        parroting metric → assembly → R7 →
            │                   Levels 1–3 + repository views
            ▼
Phase 6  PROCESS & FLEET       completion standard adopted, remaining
                                worlds migrated, compatibility layer
                                retired, final six-category report
```

Phases 2 and 3 are genuinely independent of each other (3 operates on today's chunk formats through the compatibility rule) and can interleave if Mark wants parallel tracks; the default written here is serial, sized for one builder. **Correction: Phase 4 does not depend on Phase 1 only — three of its steps need Phase 2's records.** S4.5's `native_subject_map` needs per-world records beyond the `time_window` its own caveat covers; S4.6 states outright that it "requires `contested_claim` records"; S4.7's manufactured-resolution check needs `divergence_partners`. S4.1–S4.4 are genuinely Phase-1-only and can run ahead of Phase 2 if Mark wants that ordering; S4.5–S4.7 cannot start until the relevant world has cleared S2.6. Phase 5 depends on 2 (records to assemble from) and 4 (the engine the assembly runs in). Phase 6 depends on everything.

### 2.2 The compatibility rule (how every session ends deployable)

Until Phase 6 retires it, the running system continues to read **today's artifact formats** (permanent prompt .txt, capsule .md, chunk files, `definitions.json`). Migration steps produce records *plus view generators that render those records back into today's formats*, proven by render-parity. Runtime steps (Phases 3–4) change code against today's formats. The two tracks meet only in Phase 5–6, when the assembly and the record-native paths switch on per migrated world, each behind its own checkpoint. Consequence: at no point does any step depend on another step being half-done, and a halt at any step leaves a shippable system.

## 6. Flags for Mark — sequencing findings, not redesigns

Surfaced while sequencing; each is Pass 1 applied to a case it didn't explicitly address, stated here rather than resolved silently. None changes a design decision.

- ~~F1 — Provisional divergence at first migration.~~ **Withdrawn.** §11-A's actual requirement is "mapped against **live** worlds" — all six worlds are live today, not "record-bearing" ones. Mapping `divergence_partners` against partners' existing documents (which S2.6 already does) *is* what §11 asks for, not a workaround for a gap in it. The originally-proposed `provisional: true` field was an unwarranted schema addition with no Pass 1 warrant — exactly the failure mode S1.5's own traceability check exists to catch. Dropped; see S2.6 and S6.3 below, corrected.
- **F2 — §11-A applied to already-built worlds.** The source row requires a field-bibliography sweep, search_record, and saturation statement. For migrated worlds, historical discovery data is unrecoverable (Pass 1's own backfill rule forbids inventing it). Blueprint's reading: run the sweep **at migration time** (it is cheap, and it genuinely hunts missing sources — new finds enter as new rows with real discovery data); the `search_record` documents that migration-time sweep, explicitly scoped as such; the saturation statement covers the migration-time search only. Prospective §11 applies in full to the next *new* world. Needs your OK.
- **F3 — R7's contingency, operationalized.** Pass 1 gates R7 on the parroting metric "existing," while its formal threshold is TBD-pending-baseline. The blueprint reads this as: metric exists + baseline committed + R7 configuration shows no directional worsening vs. that baseline. Stricter than the letter; consistent with its intent. Needs your OK.
- **F4 — Where the per-conversation contract lives (S4.4b).** §6.2 retires the per-round floor for a per-conversation guarantee but doesn't name the enforcing mechanism. The blueprint implements it as selector input (unheard-worlds weighting rises over the session). Implementation detail flagged because it shapes table feel — review alongside M3, since they're one decision in practice.
- **F5 — Readability gate vs. existing prompts, and this is not a hypothetical.** CO-015's own figures (grades 12.3–15.7, filed against Kimon/Eumathios) describe a superseded Representative generation — those names don't appear in any currently deployed world. But a direct, current-generation citation exists and is stronger: Imperial-Juridical-Christianity's own `Step10_Phase5_Boundary_Testing_Record.md` documents a real Register-Fidelity/readability **FAIL** on Marius's deployed prompt (an 8-sentence response averaging ~44 words/sentence, one 75-word sentence, "far outside the Framework's own Flesch-Kincaid grade 8-10 target") — and it **failed again** on the retest before holding at round three. No readability library exists anywhere in `cic-poc/backend` today (confirmed directly), so there has never been a computed check on any currently deployed prompt, on any world. The S1.3 gate applied to today's six deployed prompts is expected to find real, already-documented drift, not hypothetical drift. Any failure routes as a record/view defect to fix at that world's migration, not as a hotfix to hand-authored prompts mid-stream. Stated so a red gate on day one is understood as the gate working — and so it isn't mistaken for a new problem when it's already a known one.
- **F7 — A step authoring its own checkpoint instrument (S2.2, recurs at S5.1).** **Applied.** §0 rule 4 says a checkpoint program can't be authored in the step it must pass; S2.2's content-coverage parity script and S5.1's parroting metric were both being built inside the step they gate. Both instruments now move into S1.3 (est. sessions 2–3 → 3–4, +1 for the move), which already owns `wrs/gates/`; S2.2 and S5.1 now read as "run this step's instrument," not "build it," and S5.1's own estimate drops (1–2 → 1) to match.
- **F8 — S3.5's safety-rerun rationale, corrected.** **Applied — narrower than first stated.** On re-checking against the current document: S3.3 and S3.5 already carried an explicit safety rerun in both the Phase 3 header and their table-row checkpoints — the original framing of this flag ("the blueprint files these as not triggering the safety rule") overstated the gap, and S3.3 needed no change. The real, narrower finding survives: S3.5's stated rationale named only the modern-term bridge as the intercept it touches, when the Touches-verification pass found it also edits `epistemology_bridge.py` — a second classify-then-route intercept doing the identical query-replacement pattern, not named anywhere in Pass 1's own R9 description. S3.5's table row now names both bridges.
- **F9 — No step is named as the one that wires `wrs/parameters.yaml` into the runtime.** **Applied.** S1.4 creates the parameters file without editing anything that reads it; the first genuine runtime consumer was falling to S4.4 by accident (retiring the hardcoded turn floor) with S6.4 separately wiring the monitoring-model string. S4.4 is now stated as the deliberate first consumer — reading `wrs/parameters.yaml`'s turn-floor value is now named as part of its sub-step (a), not an incidental side effect.
- **F6 — Corrected review-cost note.** The original "≈25–35 Opus review passes" counted review-bearing *steps*, not passes — it undercounts what §4's own batch discipline requires (batch review per ~10–15 records, two-round minimum on a phase's first batch) and what S6.2 multiplies by re-running the whole Phase 2 review-bearing pipeline **five more times**, once per remaining world. Real figure is plausibly **3–4× higher: roughly 75–140 Opus review passes** end to end. That is the honest cost of "no self-reports," now stated at its real size rather than its step-count. Where you want to economize, the safest dial is still batch size in Phase 2/6 (fewer, larger batches = fewer review rounds, longer feedback loops) — never skipping a gate or parity checkpoint, which are near-free.

## 8. What "done" means

The redesign is built when: all six worlds run from records through generated views with the compatibility layer retired (S6.5 green); every §11 gate report exists per world; the Completion Standard governs the next new world before it starts; and S6.6's six-category report is on Mark's desk with real numbers against real baselines — at which point the thresholds §11-D deferred get set, once, from evidence.

The order is the commitment; the pace is Mark's.
