**Entry numbering, stated once here so it governs the whole log.** Entries are append-only. A number is never reused, reassigned, or renumbered once its entry has merged to `main` — the same discipline `reference/L3B-World-Build-Methodology/Source_Registry_Template.md` states for Registry rows: *"Append-only, no renumbering, no deletion."*

Parallel build threads are the failure case this rule has to survive, and it has already failed once. On 2026-09-09/10 two threads working at the same time each appended a different item **16** — one recording a boundary breach on `ijc.source.augustine-confessions`, one recording the post-admission source finding — because each took "the next number" from a `main` that did not yet carry the other's entry. Nothing was wrong with either entry; the numbering scheme simply has no defence against two writers.

**Resolution rule, so the next collision is mechanical rather than a judgment call:** the entry already merged to `main` keeps its number. The entry still on a branch takes the next free number *before* it lands, as part of resolving the merge. No number that has ever been on `main` changes, which is what the append-only rule exists to protect, and the collision still resolves the same way regardless of who resolves it. That is how the 2026-09-09/10 case was settled — the Augustine entry, merged first, kept 16; the source finding, still on a branch, became 17 — so no already-merged number moved.

**Citing an entry from outside this file:** give its subject and date as well as its number. A number can still change while an entry is unmerged, and a pointer that carries only a bare number does not survive that.
