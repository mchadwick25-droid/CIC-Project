# Quote Verbatim Gate — Failure Triage (2026-09-22)

Tech-Readiness Package 3, P3 relaunch thread, step 3: hand-characterize every remaining quote-verbatim failure after PR #400 (fleet sweep) and PR #401 (`verse_number` ruling). One line per record: omission / edition mismatch / nested mark / other, with the failed segment. **No record edits here** — this is the triage list only, per Mark's own instruction; record fixes are a separate session Mark will dispatch.

73 failures remain after #401's sweep (184/257 verified). All 73 are characterized below.

## Method

Each failure was traced by binary-searching the failing quote segment against its own vendored source, using the gate's own matcher (`_segment_pattern`) rather than a separate ad-hoc string search — so the break position found here is the exact position the real gate computes, not an approximation. From that break point, the source text immediately following was inspected to classify:

- **omission** — real source prose continues for several more words (a genuine sentence, not boilerplate) before or instead of what the quote has — content silently dropped with no ellipsis.
- **edition mismatch** — the quote's own continuation words were not found within a wide (4,000-character) search of the cited vendored file after the break point. Read plainly: this means the mechanical search didn't find a plausible resumption point — it does not by itself distinguish "genuinely the wrong edition/translation" from "the exact short phrase isn't literally present in this particular cited work" (e.g. a well-known saying attributed to a figure but not found verbatim in the one work cited for it). Both are real problems distinct from a silent omission; telling them apart needs the kind of scholarly judgment this mechanical pass doesn't make. Flagged as one category here, per Mark's four-way split.
- **nested mark** — the source has a quote-mark character where the record has a different quote-mark character at the same position (both genuinely marking a quotation, not a coincidence) — the class Mark ruled NOT allowed.
- **other** — doesn't fit the three above. Every "other" case below has its own specific, verified reason stated — none is a catch-all guess.

This triage pass caught and fixed three real bugs in the classification script along the way (an off-by-one that put the break word itself into the "what comes next" search, a crude non-regex anchor search that could latch onto the wrong occurrence of common phrasing, and a shallow trailing-punctuation check that stopped short of asking whether the source kept going) — each caught by cross-checking against a record whose ground truth was already independently confirmed (`pahc.quote.polycrates-to-victor`, pinned by a unit test in PR #401). Stated so the method's own limits are visible, not implied to be perfect: the **edition mismatch** bucket in particular is a "mechanical search didn't find it" result, not a scholarly confirmation of a wrong edition.

## Three patterns found along the way, not yet acted on

Beyond the four-way split, this pass surfaced three narrow, real patterns worth a decision, each affecting a small number of records — noted here, not fixed (no record edits in this PR) and not added to `ALLOWED_DIFFERENCE_CLASSES` (not this PR's ruling to make):

1. **Stray `\"` / `\'` in a record's own `text` field (6 records).** A YAML folded block scalar (`text: >-`) does not support backslash escapes — a backslash before a quote mark is literal, not an escaped quote. `pahc.quote.put-away-doubting-from-you`, `pahc.quote.they-appointed-the-first-fruits`, `desert.quote.for-thirty-two-years-i-touched-no-fruit`, `desert.quote.good-good-i-dont-mind`, `hal.quote.a-follower-of-cicero-and-not-of-christ`, `hal.quote.ever-let-the-bridegroom-sport-with-you` all carry a literal backslash character immediately before a quote mark in their `text` field — an authoring mistake, not a real character in any source. Marked in the table below.
2. **Source-side line-wrap hyphenation (2 records, both `other`).** `rzg.quote.christ-the-mirror-of-election` and `rzg.quote.mass-not-a-sacrifice` are otherwise 100% verbatim — every word present, in order — except that their vendored `.txt` source hyphenates across a line break ("eter-\nnity"), which the gate's whitespace handling doesn't collapse. Confirmed by testing both against a de-hyphenated copy of the source: both pass. The cleanest two "failures" in the whole set — arguably not failures at all.
3. **`[...]` as a single bracket-wrapped-ellipsis notation (1 record).** `cappadocian.quote.basil-against-eunomius-ant` marks its own elision as `[...]`, not a bare `...`. The gate splits ellipsis and brackets independently, so the literal `[` and `]` are left stranded at each segment's edge and treated as characters requiring a match — a parsing gap, not a content difference.

None of these three is silently handled or silently added as a difference class. They're the same kind of finding `verse_number` started as in PR #400/#401 — flagged for a decision, if and when the record-fix session picks them up or a future ruling covers them.
